# Feature: pre-v1 completion and release

Status: specified; implementation PRs and final qualification tracked separately.
Date: 2026-11-10.

## Goal

Finish the selected existing backlog as one bounded release: remaining database repairs, removal of our prebuilt CLI distribution, packaged self-hosting with Kratos authentication, SSH keys during VPS provisioning, and organization-scoped sequential deployment numbers. Separate GitHub Copilot cloud agents implement bounded tasks. Codex owns final integration testing after all required implementation PRs are merged.

Start with [the execution plan](0.execution-plan.md). Each task is an independently assignable issue/PR with explicit dependencies and file ownership. This feature groups existing requirements; it does not authorize agents to invent adjacent features or run hosted operations.

- Public product source is `muniventures/minicloud`, including API, dashboard, worker, runtime, CLI and public self-hosting assets.
- Public `main` at `83f80fa` contains merged [PR #17](https://github.com/muniventures/minicloud/pull/17): DB lifecycle/diagnostic/readiness repairs, sparse deployment-log flushing, and removal of the Intel Mac binary build. The six remaining required CI checks passed. These are baseline implementation, not tasks to repeat or proof of hosted acceptance.
- Private `muniventures/minicloud-services` owns hosted deployment/recovery workflows. Readiness commit `7751939` is committed locally and deliberately unpushed. Cloud agents cannot assume it is available remotely. Its integration remains a prerequisite for final hosted migration tests; the existing no-push instruction remains in force.
- Existing [DB repair specs](../database-release-repairs/00-execution-plan.md), [self-hosting spec](../v1.0-self-hosted-installation.md), and [SSH-key spec](../ssh-key-provisioning.md) supply the detailed requirements. The new public auth and deployment-number tasks make previously private planning accessible to public-repository agents.
- The newer source-only CLI decision in T20 supersedes the old R5 requirement to publish new prebuilt CLI binaries. It does not remove CLI functionality or server OCI images.

## Exclusions

No new dashboard redesign, performance project, billing, signup, telemetry VPS, provider, cluster, replication, failover, PITR, compatibility aliases, generic recovery API, new distribution package manager or orchestration framework. Already implemented Apps/Plans UX and application/environment behavior are integration regression targets, not new implementation assignments.

## Cloud-agent contract

1. Use one task ID and one focused PR. Read repository instructions, this overview, the task and its linked public specs. Rebase on the latest merged prerequisite commits.
2. Stay within the task's files. Shared-file work is serialized by the execution plan; obtain a handoff before widening ownership. Do not revert another agent's work or split modules merely for parallelism.
3. Include focused regression tests and run the checks relevant to the patch in the cloud environment. Record exact commands and results in the PR. Missing Docker/provider capabilities are explicit gaps, not passes.
4. Do not deploy, publish releases, purchase resources, use hosted credentials, perform operator identity conversion, clean live fixtures or claim final qualification. Synthetic tests do not establish real provider outcomes.
5. Update only the assigned task's status when submitting work. The integration owner reconciles the central plan to prevent competing tracker edits. Merge completion requires an actual merged PR, not a submitted branch.
6. Do not depend on a developer's sibling checkout, ignored helper, temporary path, local stash, secret or unpushed commit. Required reusable test code must live in the owning repository and use synthetic inputs. Raw execution output belongs in ignored `.local/artifacts/`.

## Release gate

Implementation completes when all required public and private changes are merged and their focused checks pass. Release qualification is a later Codex-owned stage: first local combined integration, then controlled staging/hosted acceptance, then any separately authorized production rollout. Record blocked cases honestly. No agent may mark the feature release-ready from its individual PR alone.
