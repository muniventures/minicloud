# Minicloud V1.0: packaged self-hosted installation

Status: specification only; implementation and installation qualification have not started.
Date: 2026-11-10.

## Outcome and release boundary

A developer installs Minicloud on a Linux VPS, opens its dashboard, creates the operator account, connects a cloud provider, and deploys an app. Installing or updating Minicloud requires no source checkout, fork, personal GitHub repository, GitHub Actions configuration, local compilation, Firebase project, or external identity service account.

V1.0 names the first packaged self-hosted product release described here. It does not reset the existing CLI version sequence or adopt the historical private roadmap's hosted SaaS/billing definition of V1. The CLI and server have independently versioned releases with an explicit compatibility contract.

Confirmed direction: distribute published images through an installer, retain manual Compose installation, simplify onboarding, and provide upgrades and recovery. The detailed defaults below are specification decisions, subject to qualification before release.

This document authorizes planning only. Product implementation belongs in this public repository. Hosted deployment workflows and operator cutover belong in `minicloud-services/`; this spec does not change or deploy that installation.

## Inspected baseline

These observations describe the local working tree on the date above, including unrelated uncommitted work. They are not claims about the deployed service or current remote branch.

| Owning source | Observed behavior |
| --- | --- |
| `docs/self-hosting.md` | Requires manual control-plane TLS, Firebase, external persistent OpenBao, SSH keys, environment configuration, and a Compose source build. It does not require a user fork. |
| `compose.self-host.yml` | Builds API, dashboard, and worker from local source; includes PostgreSQL but not the complete authentication, secrets, and HTTPS stack. |
| `modules/dashboard/Dockerfile`; `modules/dashboard/app/core/config/runtimeConfig.ts` | Installation-specific API/domain/Firebase values are compiled into the dashboard. A universal dashboard image needs startup configuration. |
| `install.sh`; `.github/workflows/cli-release.yml` | CLI distribution already uses release binaries and checksums. The existing installer installs the CLI, not the control plane. |

The separate Firebase-to-Kratos plan already selects self-hosted Ory Kratos, operator seeding, private identity administration, and host-side recovery. V1.0 depends on that product work. Its requirements relevant to a public installation are restated here so operators do not need access to the private planning repository.

## Scope

Include:

- Public, versioned API, dashboard, and worker images; installation assets and a release manifest.
- A Linux bootstrap installer and a standalone manual Docker Compose bundle using the same assets.
- Bundled persistent PostgreSQL, OpenBao, Ory Kratos, and a Caddy reverse proxy.
- Dashboard startup configuration, first-operator onboarding, and provider/plan setup guidance.
- Installation diagnostics, restart persistence, explicit upgrades, coordinated backup/restore, and host-side credential recovery.
- A documented path for the current operator to move from the existing installation, with a separately qualified preservation/restore procedure.

Exclude hosted signup and billing, public multi-user registration, Kubernetes/Helm, Docker Swarm, high availability, marketplace images, Terraform provisioning, automatic provisioning/purchase of the control-plane host, automatic unattended upgrades, and a new CLI server-management command family. App/environment VPS provisioning remains part of the existing deployment product. The deferred installation options can consume the same release assets later.

Optional telemetry, application image registries, Cloudflare automation, Google sign-in, and recovery email must not block a basic installation. Source builds remain a documented app deployment mode. Advanced external database/secrets/identity services are not part of the V1.0 acceptance matrix.

## Supported installation target

The initial qualification targets are a dedicated Ubuntu 24.04 LTS VPS on `linux/amd64` and `linux/arm64`, with persistent local storage, administrative SSH access, and public DNS pointing to the host. These are intended support targets, not claims that installation has already passed on them.

The operator supplies a dashboard hostname, its `api.` hostname, and an application domain suffix. Both control-plane hostnames need correct DNS before normal browser access. Application DNS follows the existing per-environment VPS routing model; a wildcard pointing at the control plane does not route apps on other servers.

Inbound TCP 80/443 serve HTTPS and certificate issuance; administrative SSH remains operator-managed. PostgreSQL, OpenBao, Kratos administration, and internal service ports are private. Document outbound requirements for image downloads, certificate issuance, provider APIs, and runtime communication. Do not silently change host firewall or SSH policy.

Publish measured minimum CPU, memory, and disk requirements before release. Qualification must measure the complete bundled stack, migrations, and upgrade/backup headroom. An unmeasured hardware recommendation is not a supported minimum.

The installer checks OS/architecture, storage/headroom, ports, DNS, permissions, Docker/Compose availability and supported versions, existing installation state, and required network access. It reports all actionable preflight failures before creating installation state. Default installation targets a dedicated host; refuse conflicting services or ambiguous preexisting data rather than taking ownership. Manual installation may use an operator-provided compatible Docker Engine.

## Distribution and release contract

1. Publish public OCI images to GHCR from the canonical public repository. Anonymous pulls must work; installation must not require a GitHub account or registry token.
2. Build both supported architectures. Pin Minicloud images and third-party dependencies by digest in each release manifest. Tags are discovery labels; persisted installation state records exact resolved digests.
3. Publish one release bundle containing the manifest, Compose definition, configuration schema/example, installer, maintenance tooling, checksums, release notes, upgrade prerequisites, and compatibility information. Version installer/configuration/dependency changes together with the images they operate.
4. Bind release artifacts and images to the source revision and produce verifiable release signatures/provenance. The bootstrap distribution must establish a documented trust root; a checksum fetched beside an asset detects corruption but is not independent publisher verification.
5. Permit selecting an exact release. A stable-channel installer may discover a version, but it resolves and verifies that release's own assets before installation. Never combine today's installer templates with arbitrary historical images.
6. Record the installed version, source revision, image digests, schema versions, installation ID, and last successful operation in non-secret host metadata. `GET /api/instance` reports server version and CLI compatibility through the existing instance discovery contract.

Do not change the meaning or URL of the existing CLI `install.sh` or PowerShell installer. Use a distinct server installer asset, provisionally `install-server.sh`, and a documented public distribution URL selected before publication. Any commands shown in release docs must reference real published assets.

Use `server-v<version>` tags for server releases, separate from the existing CLI `v*` trigger. Publish server GitHub releases with `make_latest=false`; the repository-wide latest release must continue serving the CLI assets expected by both existing installers. Server discovery uses an explicit server-channel manifest and exact release URLs, never repository-wide `releases/latest`. Release CI must enforce this separation before publication.

## Installation flow

### Default installer

1. The operator downloads the server installer, verifies it as documented, and runs it on the VPS. Offer an inspect-before-execution path; a shell pipeline is optional shorthand.
2. Collect non-secret hostnames and application domain, display installation paths and selected version, and run preflight. Support equivalent explicit configuration for noninteractive installs; secret inputs use protected files or stdin, never command-line arguments.
3. Install supported Docker/Compose if absent, using a documented, versioned installation path. Do not replace or upgrade an existing engine implicitly. Pull and verify the release assets/images before starting stateful changes.
4. Generate independent database credentials, signing/encryption keys, deployment SSH key material, and a short-lived one-time setup token. Initialize protected persistent directories and the bundled dependency configuration.
5. Initialize OpenBao in persistent mode, configure the required KV v2 policy, and issue scoped renewable service credentials. Normal services must not run with the bootstrap/root token. Document the restart/unseal mechanism and handling of recovery material; never store the only usable recovery material solely inside encrypted OpenBao storage.
6. Provision separate application/identity database roles and schemas, run dependency and application migrations through explicit one-shot steps, and wait for readiness before enabling normal API/worker operation. Serialize migrations; existing volumes must work without relying on empty-volume initialization scripts.
7. Obtain TLS certificates and expose the dashboard and required API routes. On DNS/ACME failure, preserve state and report how to fix and resume. Do not advertise an insecure public admin interface as a fallback.
8. Print the dashboard setup URL and separately reveal the token only in the interactive terminal or an explicitly selected protected output file. Do not place it in URL query parameters, routine logs, or diagnostics.
9. The operator enters the token over HTTPS and creates the password account and workspace in the browser. Complete seeding and transition durably from setup to ready.

Do not report success solely because containers are running. Distinguish `awaiting DNS/TLS`, `awaiting operator setup`, `ready`, and `failed`, with an actionable next step. Rerunning the same installer resumes its own incomplete operation without overwriting credentials, duplicating identities, or recreating volumes. Recognized installations use the upgrade path; unknown populated state fails closed.

### Manual Compose

Download and verify the same release bundle, supply configuration, and run the documented initialization/start sequence. No Git checkout or build toolchain is required. Manual setup invokes the same initialization, migrations, onboarding, and health checks as the installer; it is not a second implementation of those operations.

## First operator and authentication

- Bundle an instance-local Kratos service and identity database. Password-only setup requires no Firebase, Google, SMTP, or hosted Ory account. Keep Kratos administration on the private network; expose only required browser flows through the supported API/proxy boundary.
- A fresh instance admits exactly one bootstrap operator and owner workspace. Public registration is disabled. The one-time setup token is installation-bound, expires, is stored only as a verifier where possible, is rate-limited, and becomes unusable after successful setup. A host-only operation can rotate an expired token for an unclaimed instance.
- Extend the shared seed command from the auth plan to accept authenticated browser setup and protected noninteractive input. Browser setup must use that command's admission checks, not a separate account-creation path. Serialize attempts and reconcile interrupted identity creation through the exact bootstrap operation identity. Never adopt an arbitrary account by matching email.
- An already populated instance is never claimable through the setup page. Ordinary restart, installer rerun, and upgrade never reset passwords, recreate a deleted owner, or change workspace membership from stale bootstrap inputs.
- Use secure browser sessions and CSRF/origin protection under the selected Kratos/BFF architecture. Preserve API-key scopes, CLI browser approval/token login, registry authentication, runtime identities, and telemetry authentication. Display temporary identity-service outages separately from incorrect credentials.
- Provide explicit host-side password recovery for the bound operator, with session revocation, without requiring email delivery. Optional recovery email and Google login need their own configuration and qualification.

After account creation, guide the operator through adding a provider account and named plan. Explain that the first app deployment creates a billable VPS; installation and read-only provider validation create no app servers or volumes. Preserve host-key verification: installer-generated deployment keys do not authorize blindly trusting future VPS host keys. V1.0 documentation must provide a tested independent verification procedure and clear retry instructions.

## Configuration and persistent state

Use `/opt/minicloud` for installed release assets and `/var/lib/minicloud` for persistent installation state. Document effective volume mappings and secret locations; both paths can be overridden at first installation. Do not silently relocate existing data on rerun.

Separate immutable downloaded release assets, operator configuration, secrets, persistent service data, backups, and operation metadata. Protect credentials and private keys with restrictive ownership/modes. Keep configuration readable and repairable without a product source checkout. Runtime-generated logs, backups, and secrets never enter a Git repository by default; optional version control covers sanitized non-secret configuration only.

Generate dashboard public configuration at container startup or serve it through a public configuration endpoint. The same published dashboard digest must run under two unrelated domain configurations without a rebuild. Validate public values and reject invalid configuration before advertising readiness. Provider tokens, setup tokens, database credentials, signing/encryption keys, and SSH private keys never enter that public payload, image layers, or frontend build arguments.

Reserve dashboard/API/authentication hostnames using existing domain ownership rules. Reject collisions with application routing domains. Generate proxy origins, cookie scope, API discovery, and CORS configuration consistently from validated installation inputs.

Provide host-side maintenance operations for status, diagnostics, backup, restore, upgrade, setup-token rotation, and operator recovery. Final executable names are an implementation detail; their documented semantics must be shared between installer and manual installation. Diagnostics redact secrets and report health, installed version, migration/setup state, disk availability, dependency reachability, and actionable errors. Redact captured subprocess output as well as application logs.

Persist database data, identity data, OpenBao data/configuration and unseal dependencies, artifact storage, SSH keys, encryption/signing keys, proxy certificate state, and installation metadata across container recreation and host reboot. Qualify service restart ordering and renewable credentials after a cold boot.

## Upgrades

Upgrades are explicit operator actions. Show installed/target versions, supported upgrade path, required downtime, migrations, and backup status before mutation. Reject incompatible CLI/server combinations with an actionable message. Ship compatibility tests against the stated CLI range; do not rename an existing CLI release to match server V1.0.

Acquire an installation-wide operation lock, verify/download the complete target release, check capacity, and run a successful coordinated pre-upgrade backup. Block upgrade when backup or validation fails. Pause new deployments and other management writes; drain active work or stop with a retryable explanation. Do not kill provisioning mid-operation to advance an upgrade.

Apply migrations once, start the compatible target stack, and verify dependency readiness, login/session functionality, instance discovery, worker connectivity, and existing app inventory before recording success. Do not deploy, recreate, or delete customer app VPSs as part of a control-plane upgrade. Existing apps should continue serving independently; qualify this behavior with a running app during control-plane downtime.

Preserve operator configuration and secret values. Never regenerate keys or overwrite local changes with a new example file. Fail unsupported configuration with a precise remediation, and retain the previous release assets and backup.

Image rollback is allowed only when schema/data compatibility is explicitly established. Otherwise stop management writes and restore the coordinated pre-upgrade state with the matching release. Do not advertise arbitrary downgrade support or restore behind newly accepted writes. Explain recovery state when activation fails rather than falsely reporting a successful upgrade.

## Backup, restore, and removal

A control-plane backup is separate from existing customer database backup features. Capture application and identity databases, OpenBao persistent state and recovery dependencies, secrets/configuration, artifact storage, deployment SSH credentials, and installation metadata at a coordinated point while relevant writes are quiesced. Include certificate state or a tested reissuance procedure. Encrypt backup bundles and keep the decryption/recovery material separately recoverable by the operator.

V1.0 includes on-demand and scheduled backups, a documented encrypted off-host copy procedure, retention settings, visible last-success/failure status, and an isolated restore qualification. Release docs must explain what is lost if backups remain only on the VPS. WAL/PITR and a managed backup service are outside this release.

Restore verifies integrity, version compatibility, and completeness before mutation. Rehearse on a separate host with provider writes and worker provisioning disabled; restored credentials must not permit accidental concurrent management of live VPSs. Production recovery explicitly transfers control to the restored installation and fences the old worker before enabling writes. A database-only restore does not satisfy this contract.

Stopping/removing containers retains persistent data and does not delete managed app VPSs. Erasing control-plane data is a separate destructive operation requiring an exact installation target and explicit confirmation. No broad Docker prune or provider-account cleanup belongs in installation/removal.

## Existing operator transition

Fresh installation is the primary release path. Existing-installation conversion requires an inventory, backup, maintenance window, explicit identity binding under the auth plan, and an independently tested restore path. Preserve user/workspace IDs, API keys, app/environment/server identities, deployment history, secret references, encryption keys, and SSH trust. Do not infer ownership from the first user or import arbitrary old environment settings as trusted defaults.

The V1.0 release documents supported source versions and conversion preconditions. No Firebase fallback, dual authentication, general-purpose legacy importer, or silent conversion is required. Execute the actual hosted transition only as separately authorized operations work.

## V1.0 acceptance gates

1. **Fresh host:** on both supported architectures, follow public docs from a clean host to HTTPS dashboard, operator/workspace creation, CLI login, provider/plan configuration, and a successfully deployed source-built app. Require no repository checkout, GitHub credentials, Firebase, SMTP, or manual database edits.
2. **Manual parity:** repeat using only the published Compose bundle; obtain the same release digests, initialized state, and working onboarding.
3. **Universal image:** run the identical dashboard image under two unrelated hostnames/configurations with correct API/auth routing and no embedded installation secrets.
4. **Admission:** test concurrent setup, token expiry/reuse/rotation, interrupted seeding, unknown populated storage, completed seed reruns, CSRF/origin rejection, session expiry, and host recovery. No account takeover, duplicate owner, or credential reset on rerun.
5. **Persistence:** recreate containers and cold-reboot the host. Recover usable databases, identity sessions as designed, OpenBao access, keys, artifacts, TLS, and worker operation without manual secret reconstruction.
6. **Failures:** exercise bad DNS, occupied ports, failed certificate issuance, image verification/pull failure, low disk, unavailable dependencies, migration failure, and an interrupted installer. Fail clearly and resume without erasing data or reporting false readiness.
7. **Upgrade/recovery:** upgrade from each declared supported source release with an existing app, secrets, API keys, provider bindings, and deployment history. Inject failed backups, migration/activation failures, and concurrent maintenance attempts. Preserve the app's public availability and qualify the documented rollback/restore boundaries.
8. **Full restore:** restore an encrypted complete backup onto an isolated replacement host, verify operator/CLI access and secret decryption, and demonstrate fencing before production control transfer. Test recovery without access to the original host.
9. **Exposure and distribution:** prove internal/admin ports are unreachable publicly, anonymous image pulls work, release verification rejects tampering, and logs/diagnostics/public configuration contain no secrets. Confirm install and validation allocate no cloud resources. After server release publication, verify that server tags did not trigger a CLI release and both unchanged CLI installers still resolve and install the correct latest CLI binaries; verify exact-version server discovery independently.
10. **Documentation:** rehearse install, manual setup, provider connection, first deployment/SSH trust, backup scheduling/off-host copy, upgrade, recovery, and data-preserving removal using published assets. Run applicable product tests/build checks and keep qualification output under ignored `.local/artifacts/`.

V1.0 is ready only when these gates have recorded evidence and the public README clearly separates installing Minicloud, installing its CLI, and developing from source. Until then, this document describes intended behavior rather than installation guarantees.
